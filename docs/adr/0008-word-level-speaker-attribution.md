# Word-Level Speaker Attribution and Real Word Timings

Response assembly attributes speakers at word granularity, carries each ASR Adapter's real per-word timings and confidences through to the Transcription Response, and adds one additive field to the Strict Transcription Response Schema. This is a deliberate, recorded change to the Transcription API Contract.

## Real word timings replace interpolation

Both shipped ASR Adapters emit genuine per-word timing: faster-whisper produces word timestamps and per-word probabilities, and the onnx-asr adapter groups subword emission times into words with an averaged log-probability. Those values reached the response only through `raw_words`; the response's `segments[].words` and `word_segments` were regenerated by dividing the segment span evenly across its whitespace-separated words, with every `score` replaced by the constant `1.0`. The system computed accurate timings and then overwrote them. Response words are now built directly from the Project-Owned `TranscriptToken`, so `start`, `end` and `score` are the backend's own values. `score` falls back to `1.0` only when the backend supplies no probability.

## Speakers are decided per word, and segments are split on the change

Speaker attribution previously ran once per transcript segment by maximum temporal overlap, and the winning label was stamped onto every word in that segment. Any segment spanning a speaker turn therefore mislabelled every word after the turn, and the mislabelling was invisible because the words agreed with the segment by construction. Attribution now runs per word against the merged speaker timeline, and a segment run is split wherever the word-level speaker changes. Response segments are therefore speaker-homogeneous by construction rather than by assumption, and `word_segments` is the concatenation of the segments' words, so the two views cannot disagree.

Three attribution rules change with it:

- **Unknown rather than arbitrary.** A span with no timeline overlap previously defaulted to speaker `1`, silently misattributing anything falling in a diarization gap. It now receives the `-1` unknown sentinel, which was already declared and already used for spans past the diarization horizon. The `1` label survives only for an ASR-Only Server, where there is no diarization timeline at all and no speaker claim is being made.
- **Gap-bounded timeline merging.** Coalescing consecutive same-speaker entries regardless of the gap between them turned a speaker either side of a long silence into one long entry that outweighed everything inside the gap. Entries are now grouped per speaker and merged only across a gap of at most `MAX_SPEAKER_MERGE_GAP_SECONDS` (0.5 s). Grouping per speaker also fixes a second-order defect: merging previously depended on entries being adjacent in the globally sorted timeline, so an interleaved speaker blocked a legitimate merge.
- **Overlapped speech is flagged, not silently collapsed.** The diarizer emits an independent timeline per speaker, so overlapped speech appears as concurrently active entries. Taking a single maximum-overlap winner discards that. The winner is still a single label — the response contract is one speaker per word — but a word whose span contains two concurrently active speakers is marked, and a segment is marked when any of its words is.

## Contract change: additive `overlap` flag

`WhisperWord` and `WhisperSegment` in the Boundary Response Schema gain `overlap: bool = False`, mirrored on the `TranscriptWord` and `ResponseSegment` dataclasses. The schema is `extra="forbid"`, so a new field is a contract change and is recorded here rather than slipped in.

The alternative considered was encoding overlap in the existing `speaker` string as a composite label (`"1+2"`). Rejected: `speaker` is passed through verbatim into the Hypothesis STM used for cpWER, DI-cpWER and DER scoring, so composite labels would manufacture speakers that appear in no Reference STM and would degrade the very Quality Benchmark metric this work is measured by. A separate boolean keeps speaker labels scorable and keeps the flag ignorable by clients that do not want it. Making `overlap` optional with a `False` default also means existing request payloads and stored responses still validate.

The rest of the contract is unchanged: field names, field order, the five response arrays, and the OpenAI-style `json` / `verbose_json` / `diarized_json` projections all keep their existing shape.

## Spanish-aware segmentation

Segment boundaries were triggered by any of `.`, `!`, `?` or `,`. Treating the comma as a terminator fragments comma-heavy Spanish subordinate clauses into very short segments, which adds no information and makes speaker attribution noisier by shrinking the span each decision is made over. Segmentation now lives in `coro/core/segmentation.py` and applies three rules: only sentence-final punctuation (`.!?…`) closes a run; a maximum run duration (`MAX_SEGMENT_SECONDS`, 15 s) bounds long unpunctuated stretches that the comma previously bounded only by accident; and the Spanish opening marks `¿` and `¡` pull a boundary *before* the token that carries them, so an interrogative or exclamative sentence is not orphaned at the tail of the preceding segment.

These constants are module-level policy, not settings. Issue 09 runs concurrently with issue 10 in the shared-surface convention for `coro/settings.py`, and neither the segmentation nor the merge-gap value has a demonstrated need for per-deployment tuning yet. Promoting them to settings is a later step to take on evidence, not speculatively.

## Batch and streaming stay identical by construction

The Full-Memory Pipeline and the Streaming Pipeline must produce byte-identical responses. Previously the Streaming Pipeline's finalizer spilled fully assembled `ResponseSegment` rows with a provisional speaker, and assembly overwrote the label. That no longer works: word-level attribution can *split* a stored run into several response segments, so the split has to happen at assembly, once the streaming diarizer has produced its complete timeline.

The `TranscriptSpillStore` `segments` table therefore stores each finalized run's transcript tokens (`tokens_json`) instead of pre-assembled words and a speaker. Assembly calls the same `build_response_segments` the batch builder calls, one stored run at a time. Parity is a property of sharing the function rather than of two implementations agreeing, and the flat-memory guarantee is preserved because only one run is resident at a time. Segmentation is shared the same way: both paths drive `SegmentAccumulator`.

## Consequences

- `TranscriptSegment` is removed from the Project-Owned Transcript Model tree. It existed only as the intermediate the old two-phase "group, then stamp a speaker" builder needed; with attribution per word, runs go from `TranscriptToken` straight to `ResponseSegment`.
- Segment counts change for the same audio: fewer boundaries from commas, more from speaker turns and from the duration fallback.
- Consumers that assumed `segments[].words[].score` was always `1.0`, or that word timings tiled the segment span exactly, will now see real, gappy values.
